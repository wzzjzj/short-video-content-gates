# 门禁结果契约

## 保存原则

方法只保存在本 Skill；项目保存每条视频的实际门禁结果。优先修改现有记录，不创建 GATES.md、五道闸门.md、爆款规则.md 或其他平行来源。

建议写入位置：

- reference-analysis：优先写入当前选题或视频工程现有 BRIEF 的“参考视频分析”区域；尚未立项时写入项目已有的研究记录，不为单条参考另建平行门禁规则文件。
- intake、script-review、pre-production：现有 BRIEF、制作记录或 PUBLISH 的既有质量复核区域；第一次完整预览前完成，不另建一道交付门槛。
- pre-publish：仅在用户明确要求判断“能否发布”或要求智能体执行外部发布时，写入现有 PUBLISH 或发布验收区域。
- post-publish：仅在用户明确要求复盘或主动提供数据时，写入现有 PUBLISH 数据区和当前账号的数据台账。
- 状态文件只记录结论与指针，不复制完整规则。
- 用户只授权只读时，仅在回答中报告。

某一阶段尚不复核的字段写“本阶段不复核”。没有账号基线时写“当前未建立”，不得借用其他项目。

日常制作在已有记录中合并维护上述适用信息，不为每个阶段复制空白字段或问卷；只有实际发生门禁绕过时记录事故日期与说明。预览质量 PASS 必须指向已查看的实际画面和封面证据，不能由技术检查通过、用户确认或已交付倒推。

抖音 1080×1920 项目在 `pre-production` 必须以实际渲染预览、封面或首屏完成安全区、3:4 裁切和主页缩略图复核，并在第一次完整预览前内部修正。只有用户明确触发 `pre-publish` 严格审计时，才改记待发布成片和封面的文件哈希、叠层和裁切证据，并按 `release-evidence-schema.md` 生成机器证据。顶部、右侧、左下及底部三个区域对所有账号都必须检查。

本 Skill 不维护制作状态或任务完成条件。项目为门禁保存的文件事实、门禁状态和事故状态互不覆盖；“已发布”只记录事实，不代表 `pre-publish PASS`，门禁绕过一经发生应保留事故记录，不能因事后补检而删除。

## 结论优先级

- 任一 BLOCK：门禁总结果为 BLOCK，停止对应的质量放行、标记“可发布”或由智能体执行发布；不阻止清楚标注风险的本地制作交付。
- 抖音关键元素超出通用核心安全区，或当前阶段缺少规定的平台 UI、封面裁切证据：按 BLOCK 处理。
- 承诺解决问题但没有答案、判断规则或可执行方法，或承诺解释但没有明确论点：按 BLOCK 处理，不能用包装完整或技术检查通过抵消。
- 无 BLOCK 但存在 REVISE：总结果为 REVISE，修改后重新检查。
- 全部满足：PASS。
- 只有已批准并记录完整的偏离才是 EXCEPTION；未获批准仍按原问题判定。
- `pre-publish` 的平台 UI、安全区和裁切没有 EXCEPTION；共享验证器未返回 PASS 时，不得标记“可发布”或由智能体执行发布，但可以交付明确标注 BLOCK 风险的本地成片与制作资料。

## 结论失效与回退

- 改变目标观众、需求或核心承诺：回到 intake。
- 改变开头、脚本、证据结构或时长：重做 script-review。
- 改变核心结论、方法、推理、适用边界或场景兑现关系：重做 script-review；制作方案因此改变时同时重做 pre-production。
- 改变关键事实、承诺或制作方案：重做 pre-production。
- 已明确触发严格发布审计后，改变最终成片、封面、标题、发布文案、CTA、位置或团购：重做 pre-publish；未触发时不创建该阶段。
- 仅编码、封装或不改变内容的技术处理，可保留上游结论，但应确认内容一致。

## 可选的发布后回流

本节只在用户明确要求复盘或主动提供发布数据时执行；没有数据不构成待办。只与同账号、同平台、同口径的基线比较；不得混用不同账号、门店、平台、时长或指标定义。

证据等级：

1. 单条数据：观察。
2. 当前账号重复出现：项目规律候选。
3. 多账号独立重复：跨项目候选规律。
4. 用户明确批准：才可修改共享 Skill。

发布后数据不能自动训练、重写本 Skill 或改动用户规则。
